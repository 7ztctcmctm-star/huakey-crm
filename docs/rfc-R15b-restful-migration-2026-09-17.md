## 一、背景与问题

后端存在大量「动词型」端点（`/add`、`/update`、`/delete`、`/list`），不符合 REST 资源建模，也使 API 平台、权限与文档的一致性维护成本偏高。

## 二、现状（实测）

动词型端点规模（2026-09-24 对 `backend/routes/` 全量脚本统计，含子目录）：

| 形态 | 数量 |
|---|---|
| `…/add` | 26 |
| `…/update` | 21 |
| `…/delete` | 21 |
| `…/list` | **37** |
| `…/save` | 1 |
| **合计** | **106** |

分布于 20+ 个路由文件：`backup / competitor / config / contract/* / customer/* / customers / dept / finance-enhanced / followUp / integration / invoice / log / opportunity / permission / product / purchase / purchase/* / quote / role / supplier / user …`。

**已验证范式**：客户域（09-14）已迁到 `/api/v1/customers` + `/leads` + `/pool`，且新增能力只挂 RESTful 命名空间——本 RFC 直接以此为参考。

## 三、目标

把 106 个动词端点迁到 RESTful（资源 + HTTP 方法 + 路径参数），**过渡期不破坏既有调用方**，末期干净下线旧端点。

## 四、方案（已拍板）

采用「**并存 → 逐域切换 → 下线旧端点**」：

1. **只扩不收**：为每个资源新增 RESTful 路由（`POST /x`、`PUT /x/:id`、`DELETE /x/:id`、`GET /x`），与旧动词端点**复用同一 router / controller**（非复制实现，避免两套漂移）——客户域已验证。
2. 前端 api 层**逐域**切换（每域一提交，跑该域测试）。
3. 全量切换 + 观察期后**下线**旧动词端点（见第五节）。

**优先序（已拍板：问题优先、兼顾高频）**：

1. 先做「已被前端调用错配 / 已 404」的域（如 knowledge 的话术 / FAQ）——收益最大；
2. 再按业务高频域推进（客户已完成 → 商机 / 合同 / 报价 / 跟进）；
3. 其余低频配置类（backup / config / log 等）借道或收尾。

## 五、旧端点下线策略

**已确认接受破坏性变更，但不永久保留别名**，按版本化过渡执行：

| 阶段 | 动作 |
|---|---|
| v2.0 初 | RESTful 与旧动词端点双跑；旧端点响应加 `Deprecation`/`Sunset` 头并打日志 |
| v2.0 中 | 前端逐域完成切换，grep 守卫确认前端无旧路径调用 |
| **v2.0 末（或 v3.0）** | **下线旧动词端点**；下线前三查（测试引用 / 前端调用 / 文档宣传）清单为空 |

依据：本系统前端完全自控、**无外部第三方调用方**，破坏性变更风险可控；永久保留别名会持续制造两套口径与维护负担，故不采纳。

## 六、影响面

| 维度 | 影响 |
|---|---|
| API 契约 | 新增并存路由（旧契约暂不变）；v2.0 末下线旧路由 = 破坏性变更（已确认） |
| 前端 | `frontend/src/api/*.js` 逐域改路径 |
| 文档 | API 平台页宣传的端点需同步（删端点前必查「API 文档宣传」） |
| 测试 | 每域回归；新增 api 层与后端路由一致性测试（可脚本化） |
| 权限 | 权限码不变（仅路径变） |

## 七、风险与回滚

- **风险**：并存期两套路径语义漂移。**对策**：复用同一 router 对象，客户域已验证。
- **风险**：下线旧路由时漏改调用方 → 404。**对策**：三查 + 灰度。
- **回滚**：并存期可随时退回旧路径；下线后回滚需重新挂载（保留旧路由注册代码到下线后一个版本）。

## 八、验收标准

- [ ] 每个域的 RESTful 与旧端点行为一致（同 controller 双跑测试）。
- [ ] 前端 api 层无残留旧动词路径（grep 守卫）。
- [ ] 下线旧端点前三查清单为空；下线后无 404。

## 九、决策记录

2026-09-24 拍板：

1. 优先序：**问题优先（错配/404 域最先）、兼顾高频业务域**。
2. 旧端点：**接受破坏性下线，不永久保留**；v2.0 双跑 + Deprecation，v2.0 末（v3.0）下线。
