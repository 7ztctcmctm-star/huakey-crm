# RFC-R15b：全局 RESTful 迁移评估（草案）

> 编制：David ｜ 状态：**DRAFT，待评审** ｜ 日期：2026-09-17
> PRD：R-15（v2.0 起步评估，**仅出草案、不落地**）｜ 冻结相关：**是**（API 契约）
> ⚠️ 仅评估。**不落地。**

---

## 一、现状（实测，`backend/routes/`）

动词型（非 RESTful）端点规模：

| 形态 | 数量 |
|---|---|
| `…/add` | 26 |
| `…/update` | 21 |
| `…/delete` | 21 |
| `…/list` | 35 |
| `…/save` | 1 |
| **合计** | **≈104** |

分布（≥20 个 route 文件）：`backup / competitor / config / contract/* / customer/assign / customer/contact / customers / dept / finance-enhanced / followUp / integration / invoice / log / opportunity / permission / product / purchase / quote / role …`

**已收敛范例**：客户域（09-14）已迁到 `/api/v1/customers` + `/leads` + `/pool`，且新增能力只挂 RESTful 命名空间——**这就是本 RFC 的参考范式**。

## 二、目标

把 ≈104 个动词端点迁到 RESTful（资源 + 方法 + 路径参数），**不破坏既有调用方**。

## 三、方案（推荐 C：借道渐进，不做大爆炸）

- **方案 A（不推荐）**：一次性全量替换 → 触及所有前端 api 层 + 文档，回归面巨大。
- **方案 B**：冻结现状，新端点才 RESTful → 债务永久留存。
- **方案 C（推荐）**，分三步：
  1. **只扩不收**：为每个资源新增 RESTful 路由（`POST /x`、`PUT /x/:id`、`DELETE /x/:id`、`GET /x`），与旧动词端点**并存**（同一 controller，避免两套实现漂移——客户域 09-14 已验证此范式）。
  2. 前端 api 层逐域切到 RESTful（每域一提交，跑该域测试）。
  3. 全量切换 + 观察期后，**下线**旧动词端点（参照客户域「老树整树下线」做法）。
- **优先序建议**：先做「已被前端调用错配」的域（如本轮修的 knowledge），收益最大；其余按 PRD 扩展节奏借道。

## 四、影响面

| 维度 | 影响 |
|---|---|
| API 契约 | 新增并存路由（旧契约暂不变）；末期下线旧路由 = **破坏性变更**，须通告 |
| 前端 | `frontend/src/api/*.js` 逐域改路径 |
| 文档 | API 平台页宣传的端点需同步（历史教训：删端点前查「API 文档宣传」） |
| 测试 | 每域回归；`api/*.js` 与后端路由一致性测试（可脚本化） |
| 权限 | 权限码不变（仅路径变） |

## 五、风险与回滚

- 风险：并存期内**两套路径语义漂移**。**对策**：复用同一 router 对象（非复制实现），客户域已验证。
- 风险：下线旧路由时漏改调用方 → 线上 404。**对策**：三查（测试引用 / 前端调用 / 文档宣传）+ 灰度。
- 回滚：并存期随时可退回旧路径；下线后回滚需重新挂载。

## 六、验收标准（草案阶段）

- [ ] 每个域的 RESTful 与旧端点**行为一致**（同 controller 的测试双跑）。
- [ ] 前端 api 层无残留旧动词路径（可 grep 守卫）。
- [ ] 下线旧端点前，三查清单为空。
