# RFC-R15a：Opportunity 8 阶段评估（草案）

> PRD：R-15（v2.0 起步评估，**仅出草案、不落地**）｜ 冻结相关：**是**（Opportunity 属冻结闭环）
> ⚠️ 仅评估。

## 一、现状（实测）

机会阶段现为 **6 阶段**，存于 `crm_opportunity.stage TINYINT`：

| stage | 名称 |
|---|---|
| 1 | 询盘 |
| 2 | 需求确认 |
| 3 | 方案报价 |
| 4 | 谈判 |
| 5 | 成交 |
| 6 | 失败 |

**⚠️ 关键发现：该映射在 ≥4 个服务里重复硬编码**：
- `services/analysisService.js:186` 与 `:216`（同一文件两处）
- `services/reportAnalyticsService.js:63`（数组）与 `:438`（对象）——两种形态并存
- `services/searchRouteService.js:9`（`STAGE_MAP`）
- `services/opportunityService.js:228/284/606/631`（硬编码 `5`/`成交`）

⇒ 任何阶段变更都需改 ≥4 处，漏一处即产生口径不一致（漏斗/报表/搜索各说各话）。

## 二、目标（8 阶段）

把阶段从 6 扩为 8（PRD 目标），且**消除重复映射**（单一事实源）。

## 三、方案（推荐 A）

### 方案 A：单一阶段字典 + 数据映射迁移（推荐）
1. 新增 `backend/constants/opportunityStage.js`（**唯一事实源**）：`{1:'询盘',...,8:'…'}` + 前进/回退规则 + 阶段分组（open/won/lost）。
2. **收敛**：`analysisService`/`reportAnalyticsService`/`searchRouteService`/`opportunityService` 全部改为引用该字典（替换 4+ 处重复）。
3. **迁移**：`stage` 语义变化 → 需**数据映射**（旧 1-6 → 新 1-8），并处理「失败」在 8 阶段模型中的位置（是终止态之一还是独立维度）。
4. **前端**：漏斗（R-05 已透传 `stage_code`）、筛选、看板同步新字典。

### 方案 B：只加不重构（不推荐）
直接改 4 处映射为 8 阶段 → 债务更深，下次还要改 4 处。

## 四、影响面

| 维度 | 影响 |
|---|---|
| 表结构 | 若 stage 语义重排 → **数据迁移 + 可能改列注释**（冻结表，需 RFC） |
| 后端 | 4+ 服务映射收敛；`opportunityService` 前进/回退守卫规则重定义 |
| 前端 | 漏斗/筛选/详情阶段展示 |
| 报表 | 漏斗、赢单率、阶段分布口径 |
| 数据 | 存量机会的 stage 重映射（**必须先出映射表并干跑**） |

## 五、风险与回滚

- 风险：**8 阶段 vs 现有 5=成交 的硬编码**（如报价转合同推进到 `stage 5`）若重排会直接错位。**对策**：新增阶段尽量**追加**在边界（如 7/8）而非插入中间，避免重排；确需插入则必须全量数据迁移 + 干跑。
- 回滚：字典文件 + 4 处引用可回退；数据迁移须可逆（保留映射表）。

## 六、验收标准（草案阶段）

- [ ] 阶段字典单一事实源，全仓无第二处映射（可加 grep 守卫测试）。
- [ ] 8 阶段漏斗/报表/搜索口径一致。
- [ ] 存量数据映射干跑无丢失/错位。
