## 七、补充修复（2026-09-17 晚，由新增 E2E 抓出）

### 7.1 🐛 真 bug：迁移 116 列名偏离约定 → `/approval/rules` 500

| 项 | 内容 |
|---|---|
| 现象 | R-08 新增的 `approval-rule.spec.js` 跑起来后，后端报 `Unknown column 'r.create_time' in 'field list'`（`approvalService.listApprovalRules`） ⇒ **审批规则列表接口 500** |
| 根因 | 迁移 116 建表用了 `created_at/updated_at`，而**项目主流约定是 `create_time/update_time`**（create_time 85 表 / update_time 46 表；同族 `crm_approval_record/workflow/step` 也全是 create_time/update_time），服务层 SQL 用的是约定名 ⇒ 列名错配 |
| 为何单测没抓到 | 后端单测 mock 了 DB，**列名错误在 mock 下不可见** —— 只有真实库/E2E 才会暴露 |
| 修法 | 对齐约定：迁移 116 改 `created_at→create_time`、`updated_at→update_time`（附注释警示）；服务层 SQL 无需改 |
| 验证 | 直连 API：`GET /approval/rules` → **HTTP 200 + 数据**（含 `create_time`）；`crm_approval_rule` 列名实测为 create_time/update_time |

### 7.2 基线二次重生成（因 7.1 改了迁移）

- **又撞系统性陷阱**：当前基线**已含** `crm_approval_rule`，而迁移 116 是 `CREATE TABLE IF NOT EXISTS` ⇒ 表已存在 → 整段跳过 → 旧列名残留。
- 修法：regen 流程中**导入基线后先 `DROP TABLE crm_approval_rule`** 再跑迁移，让 116 按新列名重建。
- 结果：`deploy/init-complete.sql` diff **恰好 4 行**（两个列名）；新基线建库 **104 表**；`N-05 verify` → **92/92 PASS**。

> 结论：**R-08 的 E2E 投入立刻回本**——它抓出了一个后端单测（mock DB）无法发现的真实 500 缺陷。
