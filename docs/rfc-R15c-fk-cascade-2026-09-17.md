# RFC-R15c：FK CASCADE 统一评估（草案）

> ⚠️ 仅评估。**不落地。**

---

## 一、现状（实测，`huakey_crm`）

**外键删除规则四分五裂**（共 99 个 FK）：

| DELETE_RULE | 数量 |
|---|---|
| `CASCADE` | **41** |
| `SET NULL` | 48 |
| `NO ACTION` | 7 |
| `RESTRICT` | 3 |

**指向 `crm_customer` 的 FK 尤其危险**：

| DELETE_RULE | 指向 crm_customer 的 FK 数 |
|---|---|
| `CASCADE` | **11** |
| `SET NULL` | 9 |
| `NO ACTION` | 1 |

**与项目既定策略的冲突**：
- 项目红线：「**删数据先想历史**」；域内大量**软删除**（`deleted_at`/`is_deleted`，60 处软删列，覆盖 106 表中的多数业务表）。
- ⇒ 若对客户做**硬删除**，11 个 CASCADE 外键会**连带硬删**关联的报价/合同/跟进等业务记录 → **历史不可恢复**，与软删除策略直接冲突。

## 二、目标

统一 FK 删除规则口径，使**硬删除不再意外级联销毁业务历史**。

## 三、方案（推荐 C：口径统一 + 定向整改）

- **方案 A（不推荐）**：全库统一为 `RESTRICT` → 波及面大，且部分「附属表」确应随主表清理（如纯明细）。
- **方案 B**：不动 → 风险持续。
- **方案 C（推荐）**：
  1. **定义口径**（写入规范）：
     - 业务主数据（customer/opportunity/quote/contract/payment…）→ **`RESTRICT` 或 `NO ACTION`**（禁止级联硬删，删除须显式走软删）；
     - 纯附属明细/日志（如 `*_item`、`*_log`）→ 视情况 `CASCADE`（随主表清理无语义损失）；
     - 弱引用/可空归属 → `SET NULL`。
  2. **定向整改**：优先处理**指向 `crm_customer` 的 11 个 CASCADE**（改 `RESTRICT`），因其直接威胁客户历史完整性。
  3. 逐条评估 + 迁移（`ALTER TABLE ... DROP FOREIGN KEY / ADD ... ON DELETE RESTRICT`）。

### ⚠️ 前置前提
改 FK 删除规则**只影响「删除行为」**，不影响查询——但**执行前必须确认**：现有的删除路径是否**依赖** CASCADE 自动清理？若依赖，改规则会导致删除报错（1451）。⇒ 必须先审计所有硬删除入口。

## 四、影响面

| 维度 | 影响 |
|---|---|
| 表结构 | 最多 41 处 FK 规则变更（冻结表 → 需 RFC） |
| 后端 | 任何**硬删除**逻辑需重估（可能需改为软删除） |
| 数据 | 变更不迁移数据；但改变未来删除语义 |
| CI/基线 | 基线重生成 + N-05 verify（`check-fk-details.sql`）更新 |
| 归档/备份 | 备份恢复演练需覆盖新约束 |

## 五、风险与回滚

- 风险：现有硬删除入口依赖 CASCADE → 改 `RESTRICT` 后**删除失败**。**对策**：先 `grep` 所有 `DELETE FROM` 入口，逐个确认；对确实需要删主表的场景改软删除。
- 回滚：FK 规则可逐条改回（DDL 可逆）。

## 六、验收标准（草案阶段）

- [ ] 全库 FK 删除规则符合口径（脚本化探测，纳入 N-05）。
- [ ] 指向 `crm_customer` 的 FK **无 CASCADE**。
- [ ] 所有硬删除入口审计完成，无 1451 报错。
