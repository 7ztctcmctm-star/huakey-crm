# RFC-R13：`owner_id` / `create_by` / `created_by` 命名统一评估（草案）

> 编制：David ｜ 状态：**DRAFT，待评审** ｜ 日期：2026-09-17
> PRD：R-13（全局）｜ 冻结相关：**是**（触及多表列名，属契约级）
> ⚠️ 仅评估。PRD 明确：**输出统一命名规范 + 受影响清单，不强制一次性改表**。

---

## 一、现状（实测，`huakey_crm` 全库 106 表）

| 列名 | 语义 | 出现表数 | 所在表 |
|---|---|---|---|
| `create_by` | 创建人 | **37** | 大多数业务表 |
| `created_by` | 创建人 | **1** | `crm_purchase_comparison` |
| `owner_id` | 归属人（负责人） | **5** | `crm_customer`、`crm_opportunity`、`crm_supplier`、`crm_purchase_order`、`crm_follow_up_reminder` |

> 注：`_migration_097_backup` 为迁移内部备份表，不计入应用结构。

**三个问题**：
1. **同义不同名**：`create_by` vs `created_by`（仅采购比价表不同）。
2. **归属人语义未统一命名**：`owner_id` 仅在 5 张表，其余表若要表达「归属」则无统一列。
3. 缺少书面规范 ⇒ 新表各写各的（本 RFC 即为补上此规范）。

## 二、拟定命名规范（提案）

| 语义 | 规范列名 | 说明 |
|---|---|---|
| 创建人 | **`created_by`** | 与主流 ORM/工程习惯一致；`create_by` 为历史遗留 |
| 更新人 | **`updated_by`** | 若存在，一并规范化 |
| 归属人（负责人） | **`owner_id`** | 语义独立于「创建人」，保留并推广 |
| 创建/更新时间 | **`created_at` / `updated_at`** | 现状混用 `create_time`/`update_time`，一并评估 |

> ⚠️ 现状大量使用 `create_time`/`update_time`（而非 `created_at`/`updated_at`）。是否改时间列名需单独评估（影响面更大）。

## 三、方案（推荐 C：渐进式，不一次性改表）

- **方案 A（不推荐）**：一次性 `ALTER` 37+1 张表重命名 → 高风险，破坏冻结契约，前端/后端全量改动。
- **方案 B**：仅新增表遵守新规范，旧表不动 → 命名继续分裂。
- **方案 C（推荐）**：
  1. **本 RFC 作为规范落文档**（`docs/` 命名规范）；
  2. **新表强制**用 `created_by`/`updated_by`/`owner_id`；
  3. 旧表**按需**在「该表本就要改」时顺带统一（借车改道），不单独立项；
  4. 代码层可加**适配层**（查询时统一别名），但不超过一处 helper。

## 四、影响面（若未来执行重命名）

| 维度 | 影响 |
|---|---|
| 表结构 | 38 张表列名 + 索引/外键引用 |
| 后端 | 全部涉及该列的 SQL、JOIN、INSERT 列表 |
| 前端 | 字段名出现处（api 层/表单） |
| 数据/备份 | 备份脚本、导入脚本 |
| CI/基线 | 基线重生成 + N-05 verify 更新 |

## 五、风险与回滚

- 风险：一次性重命名易产生「漏改一处」的隐性 500。**对策**：不做一次性批量改；规范先行，改表借道。
- 回滚：方案 C 无表结构变更，零回滚成本。

## 六、验收标准（PRD 原话）

- [x] 输出统一命名规范文档 + 受影响清单（**本 RFC 即交付物**）。
- [ ] 不强制一次性改表（遵守）。

## 七、待拍板

1. 规范列名取 **`created_by`** 还是 **`create_by`**？（现状 37:1 倾向 `create_by`，工程习惯倾向 `created_by`）
2. **时间列名**（`create_time` vs `created_at`）是否同期评估？
3. 是否需要「新表提交前 lint」守住规范（脚本化）？
