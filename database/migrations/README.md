# 数据库迁移说明

本目录存放铧旗 CRM 的 MySQL 8.0 数据库迁移脚本。

## 命名规范

- `XXX_description.sql`：正向迁移脚本
- `XXX_description_down.sql`：对应的回滚脚本
- 编号采用三位数字，按字典序执行

## 历史事件：`109` 改号为 `111`

`111_remove_dead_permission_codes.sql` 文件头自述：

> 原编号 109，因生产库已应用未入库的 `109_follow_up_opportunity`
> （migrate.js 按数字前缀去重，109 版本号已被占用），改号为 111。

**这说明存在过一种做法：在生产库执行了尚未入库的迁移文件。**

**为什么必须避免**：
- `migrate.js` **按数字前缀去重**（记录在 `schema_migrations.version`），
  一旦某版本号被执行过，仓库里同号的迁移会被**静默跳过**；
- 因此仓库与生产库的迁移状态**不可互推** —— 只看仓库无法知道生产实际执行过什么；
- 后续迁移会被迫跳号或改号，进一步加剧编号不连续；
- 若该未入库迁移的内容与仓库后续版本不一致，排查会非常困难。

**建议（流程层面，待团队确认）**：

| 建议 | 理由 |
|------|------|
| 迁移文件**先入库、再上生产** | 保证仓库是迁移状态的唯一事实来源 |
| 若已在生产执行过未入库迁移，**必须回补入库**（哪怕空占位） | 占住版本号，避免后续撞号 |
| 上生产前核对 `SELECT version FROM schema_migrations ORDER BY version` 与仓库文件列表 | 提前发现错位 |

## ⚠️ 关于测试库 / CI 的迁移状态（重要）

E2E 与 CI 的数据库自举方式为：**导入 `deploy/init-complete.sql` 基线，
然后把「所有」迁移版本直接标记为已执行**（见 `.github/workflows/ci.yml`）。

**即：测试库绕开了迁移链，迁移脚本本身从未真正执行。**

由此产生两个必须知道的影响：

1. **测试库的 `schema_migrations` 反映的是仓库文件列表，不是"实际执行过什么"**；
2. **依赖迁移写入的数据在测试库中可能不存在**。已发现的实例：
   迁移 `086_fix_sales_permissions.sql` 给 `sales` 等角色授予了 `ai` 权限，
   但测试库里没有 `sales` 角色 —— 若只看测试库会得出错误结论。

> **需要验证迁移链本身时，必须在空库上真实执行 `run_migrations.js`，不能依赖测试库。**

## 执行方式

迁移由 `database/run_migrations.js` 在应用容器启动时自动执行。
脚本会按文件名字典序依次运行，并在 `schema_migrations` 表中记录已执行的版本。

## 新增迁移检查清单

```
□ 编号 = 当前最大编号 + 1（当前为 111，下一个是 112；写前再确认一次）
□ 同时提供 _down 回滚脚本
□ 写成幂等：可重复执行不报错
□ 表/列存在性先用 information_schema 判断，再 ALTER
□ 涉及数据回填时，写明回填范围与失败后的处理方式
□ 文件头注释写明：变更内容、背景、风险等级
□ 先入库、再上生产（见「历史事件」一节）
```
